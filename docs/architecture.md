# TradePilot research architecture

## Scope

The implemented system is a Python research workspace. It has no frontend,
Node.js API, AI explanation service, live execution, or broker order routing.
It consumes synthetic or explicitly supplied licensed market data and produces
auditable research artifacts.

## Architectural layers

| Package | Responsibility |
| --- | --- |
| `tradepilot.core` | Dependency-free canonical JSON and hashing compatibility utilities |
| `tradepilot.data` | Candle contracts, normalization, provider adapters, ingestion, sessions, immutable datasets, integrity and readiness checks |
| `tradepilot.indicators` | Provider-independent EMA, Wilder RSI and Wilder ATR calculations |
| `tradepilot.strategies` | Deterministic breakout and EMA/RSI pullback candidate detection |
| `tradepilot.reporting` | Canonical candidate-report models, validation, storage and verification |
| `tradepilot.backtesting` | Events, order lifecycle, execution policies and deterministic simulation |
| `tradepilot.accounting` | Trade reconstruction, conversion, ledger, equity and metrics |
| `tradepilot.validation` | Chronological partitions, walk-forward analysis, cost stress, uncertainty and locked-test governance |

The intended dependency direction is:

```text
core
  |
data -> indicators -> strategies -> reporting -> backtesting -> accounting
  \______________________________________________________________/
                              |
                         validation
```

Backtesting legitimately consumes candidate reports and verified datasets.
Accounting consumes immutable simulation results. Research validation composes
all lower layers. CLI modules may compose their package and lower layers.

Known boundary exceptions are documented rather than hidden:

- `tradepilot.data.readiness_pipeline` orchestrates indicators, strategies and
  reports and is therefore an application workflow located inside `data`.
- The batch-import CLI seals research partitions after publishing a dataset.

These are candidates for later incremental refactoring. Canonical JSON and
SHA-256 helpers now live in dependency-free `tradepilot.core`; the former
`tradepilot.reporting.canonical` path remains a compatibility re-export.

## Domain invariants

- Candle timestamps are UTC candle-opening times.
- A completed H1 candle becomes observable one hour after its opening.
- Prices and monetary values use `Decimal`.
- BID and ASK are preserved; midpoint values are never relabeled as BID/ASK.
- Missing candles are classified, never fabricated.
- Datasets, candidate reports and research results are immutable and
  content-addressed where implemented.
- Retrieval and creation timestamps are metadata and are excluded from content
  identity where specified by their models.
- Structural invalidation references are research evidence, not executable
  stop-loss orders.
- Locked-test partitions are not evaluated without separate authorization.

## Identity compatibility policy

Dataset IDs, canonical checksums, source-artifact checksums, candidate-report
IDs, simulation IDs, accounting-report IDs, validation-report IDs and partition
IDs are compatibility contracts. Refactoring must preserve them for identical
content.

`research/tests/test_identity_golden.py` stores literal trusted bytes and hashes.
Expected values must never be generated by the implementation during an
assertion. A proposed identity change requires:

1. a written schema/version decision;
2. an explicit migration and backward-verification plan;
3. preservation of existing immutable artifacts;
4. review of canonical field order, Decimal and timestamp encoding;
5. separate approval before updating any golden value.

Changing a golden constant merely to make a failing refactor pass is prohibited.

## Reproducibility boundary

Canonical JSON sorts object keys, uses compact UTF-8 JSON, preserves finite
Decimals as exact strings, and normalizes aware timestamps to UTC `Z` form.
SHA-256 is used for content identities. Provider retrieval time and report run
creation time remain separate metadata when the corresponding model specifies
that exclusion.
